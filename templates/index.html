Archipelago Multi-World Project

This is one of the projects I'm most proud of, it was also my first experience in working with a large codebase and contributing to an open source project!

In this project, I worked on adding the Gameboy Advanced game ‘Mega Man Zero 3' to a community-driven open source project called Archipelago. I started it because I wanted to challenge myself, improve my programming skills, and be part of a creative project that other people could enjoy.

This project pushed me to learn a lot of different areas at once. I wrote Python and Lua scripts that interact with emulators, I reverse engineered out how the game's RAM/ROM works, and even edited the game's assembly code so it could handle new logic. I spent time experimenting, testing, and building tools until I got everything working together.

What I like about this project is that it shows how far I've come as a developer. It combines higher-level programming with low-level memory work, network communication, and a good bit of problem solving. It's technical, but it's also something I did because I care about the game and the community that plays it.

1. What is Archipelago

Archipelago is a big community project that connects different games together. It's known as a “multiworld randomizer,” which means that items in one player's game can appear in someone else's. If I pick up an upgrade in Mega Man Zero 3, that item might actually go to a friend who's playing a completely different game, like The Legend of Zelda or Super Metroid.

Every game that connects to Archipelago is called a “world.” Each world defines the game's items, locations, and progression rules. The server handles all the item distribution behind the scenes, with the client for each game handling the updates through the player's memory or save data when new items are received.

What makes this so fun is how it turns a normally single-player activity of playing a randomizer into a multiplayer experience. Players can talk, strategize, and depend on each other to make progress.

My goal was to make Mega Man Zero 3 work as one of those worlds. That meant figuring out how the game stored its inventory, how to detect progress, and how to write data back into the game when items were sent over the network.

2. Prototyping

The first steps I took towards this project was understanding the game's internals and creating a quick prototype.

The main aspect of the game that would be randomized are the game's ‘Secret Disks'. These are collectables that appear throughout the game, either in secret locations or dropped from enemies. Opening them rewards the player with useful upgrades, in-game currency, or one time use power ups. Randomizing them and incorporating them into the Archipelago would be a great place to start.

To find out how to do this, we need to understand how the game stores these items. As the game is running, every piece of information regarding the game is stored in various RAM values. However, these RAM values are not possible to understand by just looking at them, we need to do some reverse engineering.

Many emulators have built in tools that let you view and manage RAM addresses, such as the RAM Search tool in the Bizhawk Emulator. This tool allows you to search for RAM values that meet certain criteria.

For example: if we wanted to look for the health value of the player, a good idea would be to set an initial search and eliminate any RAM values that are currently changing. Any values changing at this point would be related to things such as global timers, animation values, positions for other entities, etc. Once these have been narrowed out, we can then do something to change our health value, such as taking damage from an enemy. We can now narrow down our search to filter out only RAM values that have decreased since the last time we checked. Once we have a smaller list of values to look at, we can begin poking these addresses individually with higher or lower values to see how the game reacts. Once we find an address that correlates with our health bar, we are done!

Using this process, we can find RAM addresses that store whatever we want. We can locate the player's inventory by collecting an item and seeing what RAM values get updated. This led me to discovering a series of Bytes that store information regarding the player's inventory. These bytes are stored as bitflags, which are easily reversible into the item that they represent.

For example, the RAM value for the first byte might say ‘AA' or something similar. The first digit represents whether or not the item has been opened, while the second represents whether the item has been found or not. We can convert ‘A' into binary, which gives us the following: ‘1010'. This specifically would mean that the player has found the second and fourth item in that slot (going from left to right).

From here, I can write a simple Lua script running on the emulator in order to track the items that the player has received.
Note that the items collected in the video matches up with the items printed in the Lua script. This proves that this project can work!

3. Understanding Archipelago Infrastructure

This was probably the most difficult part for me to understand. As mentioned before, I was brand new to working with large codebases prior to this project, so I was in for a lot of learning.

Luckily, Archipelago has a very talented and welcoming community, as well as concise and helpful documentation. Using other completed projects as a base, I was able to understand each component that I had to work on.

Each world is going to be laid out differently, as each game is going to have different implementation and requirements. For a game like mine, we need:

__init__.py: A starter file that creates the world object so that Archipelago recognizes it. Also handles creating the logic for the randomizer and anything else the Archipelago object needs from my world.

Client.py : The most important file, this is the logic that determines how the emulator and the Archipelago world interact. Most of my time spent developing was managing this file.

Items.py / locations.py / regions.py / regions.py : Files for documenting and organizing different items and collectables in game.

Options.py : Uses information provided by the user to make modifications to the client or ROM generation.

According to the Bizhawk client documentation, the Bizhawk client connects to a Lua script that was developed by the Archipelago community. This script takes function calls to pull or insert RAM data into the emulated game.

The Archipelago server processes this information and potentially sends a packet back to our client (remember that this is a multigame randomizer, an item is likely to be sent to another player instead).

This is about the general idea of how the Client works. There are many more issues and edge cases that needed to be addressed. One of the biggest issues was making sure that if you were given an item through Archipelago, that the given item would still be collectable in your world.

For example, if another player gives you, say, secret disk #7. You are given the item, and since the game thinks you found it, the game will not show you secret disk #7 in game, meaning it is uncollectable, and the item associated with collecting it is gone.

This issue was corrected through the use of multiple inventories handled by the client. One inventory is used when you are in a level, which are the areas secret disks are collected. While another inventory is used while you are present in the Hub area, where secret disks are opened and the items are equipped.

In addition to this, we need to keep track of the levels the player has beaten, which non-secret disk items the player has collected, the level the player is on, etc. There is simply too much to cover regarding this, so check out the project's source code if you want to learn more!

5. Patching the Game Using Assembly

Having the game read and write memory is a good starting point, but it is still the bare minimum for a world within the Archipelago framework. Understanding where to go from here requires a lot of understanding on why players play randomizers. One of the biggest aspects of a randomizer is that it should change up the gameplay as well as progression order. With the current implementation no part of the progression is changed. The only items in the secret disks are optional bonuses. Ideally, the order in which you play the game should be completely changed with each playthrough.

This level of modification is not going to be accomplished with just memory edits through Archipelago. From here we will need to edit the game's ROM, and that means using assembly. Let's work through the process of finding an instruction we want to edit.

Let's find the instruction that deals damage to the player. First we would want to find the RAM address for the player's health, we can do this using RAM watching methods we discussed previously. Once we find this address, we can set a breakpoint on it. Breakpoints for these addresses can either be on read, write, or execution. We want to know when it gets written to. As you can see in the bottom left debugger window, the address 8007CBA is the instruction that stores a register value to our health address in RAM. We can trace upwards in the instructions to find where this register value comes from. Here we can see that a value gets loaded, this is likely a damage value table, or an individual damage value located in a struct for each enemy. Here that value gets loaded, then subtracted to our current health. Afterwards, this new health value is stored in RAM, thus damaging the player.

Using this method, and with enough trial and error, we can trace any instruction that we want to modify and even add our own new instructions! SF6 Scraper

This project is my attempt to bring player data from Street Fighter 6 to an easy to use web application. It's a custom web application that scrapes, organizes, and displays online player statistics directly from Capcom's official servers, showing match history, win rates, character usage, and most importantly, information on the player's matchmaking rating (something missing from the official site!)

I started this project because I wanted to learn more about full-stack development. More specifically combining web scraping, databases, and front-end design while also building something connected to a game I enjoy.

1. How the Site Works

When a user visits the site, they can enter their in-game Player ID into a form on the homepage. Once submitted, the website launches an automated headless browser behind the scenes using Playwright, a Python framework for browser automation.
The scraper logs into Capcom's official CFN (Capcom Fighters Network) service using a private account, then navigates to the player's public profile and gathers data like:

  • Recent ranked matches
  • Character choices
  • Match results and ratings (MR/LP)
  • Opponent information

All of this data is parsed and inserted into a MySQL database hosted on the backend. Once the information is stored, the user is automatically redirected to a stats page that displays charts, tables, and summaries built from the newly collected data.

If the player has been searched before, the scraper doesn't need to run again, as the data is fetched directly from the database for instant loading. In the future, there will be another system that automatically searches for new games and adds those into the database.

2. Technical Details

The project is hosted on PythonAnywhere, which runs the main Flask web application. Flask handles user requests, routing, and integration with the MySQL database. The Playwright scraper runs as part of the same system, launching a headless Chromium browser in a sandboxed environment.

The database schema consists of two key tables:

  • users — stores each player's ID and username
  • matches — logs all match details, including both players, their characters, match ratings, and outcomes
From there, additional scripts and helper functions process the scraped data and update visual components such as player dashboards and recent match feeds.

3. Challenges and Learning

One of the biggest challenges was working around Cloudflare's verification system and Capcom's login requirements. The scraper needed to simulate human-like interaction. Logging in, waiting for page loads, and navigating multiple redirect pages, all while remaining reliable on a remote host.

Optimizing performance was another major focus. Because each new user request triggers a full scrape, I had to make sure that the scraper reused sessions efficiently and committed data to the database safely without blocking other users.

Just like I mentioned before, this site is still a work in progress. Most of the planned features are listed on the main landing page, with more detailed statistics being the current major focus.
